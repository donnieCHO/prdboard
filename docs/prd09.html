PRD: 교사 업무 자동화 유틸 2종 — 수업 슬라이드 자동 제작 · 학교생활기록부 자동 점검

작성일: 2026-11-25 문서 성격: 제출용 제품 요구사항 정의서 (2026-11-22 제출본에 유틸 1종 추가)

1. 취지

1.1 문제의식: 저비용으로 교사의 시간을 어떻게 돌려줄 것인가

  • 교사의 시간은 수업보다 수업 준비와 행정 업무에서 더 많이 빠져나간다. 교재를 수업 자료로 옮기는 일, 학기 말 생활기록부를 한 줄씩 대조하는 일이 대표적이다.
  • 인공지능으로 이 일을 줄일 수 있다는 것은 이미 알려져 있다. 그러나 학교 현장에서는 다음이 걸림돌이다.
    • 비용: API 호출은 쓴 만큼 돈이 든다. 학교·개인 교사가 따로 예산을 잡기 어렵다.
    • 설치·조작: API 키 발급, 프로그램 설치, 명령어 입력은 대부분의 교사에게 장벽이다.
    • 개인정보: 학생 기록을 외부 AI로 보내는 일은 허용되기 어렵다.
  • 그래서 질문을 이렇게 세웠다. "어떤 선생님이라도, 추가 비용 없이, 별도 조작 없이, 시간을 많이 쓰는 일을 자동화할 수 있게 하려면 무엇을 빼고 무엇을 더해야 하는가?"

1.2 답: 이미 쓰던 두 도구를 하나는 보강하고, 하나는 열화하여 출품

두 도구 모두 이미 현장에서 쓰던 것이다. 원래는 둘 다 인공지능 호출(로컬 CLI·API)에 기대는 구조였다. 출품을 위해 각 업무의 성격에 맞게 방향을 정반대로 잡았다.

구분수업 교재 슬라이드 자동 제작학교생활기록부 자동 점검
기존 방식사용량이 충분한 로컬 CLI를 앱이 직접 호출해 작업을 지시하고 바로 결과를 받는 구조엑셀 자동화는 거의 갖춰져 있었으나 판정은 API 중심, 기계적 점검은 오류를 판독하는 수준
걸림돌선생님들은 CLI를 잘 모르고 MCP 같은 연결 방식도 모른다API 호출 비용과 학생 기록 외부 전송 문제
이번 방향보강 — 연결 방식을 선생님 눈높이로열화 — API를 완전히 걷어 냄
바꾼 내용웹 페이지에서 로컬 에이전트와 직접 소통하는 방법을 만들어, 선생님이 이미 구독 중인 어떤 AI 에이전트라도 붙여 쓰게 함API를 완전히 제거하고, 결정적 규칙 코드의 기계적 점검을 API 수준에 가깝게 끌어올림
왜 이 방향인가슬라이드 제작은 창작이 필요해 AI가 꼭 있어야 한다. 대신 비용은 이미 내고 있는 구독료로 해결한다점검은 지침 대조가 중심이라 규칙을 촘촘히 하면 충분하다. API를 빼면 비용·개인정보 문제가 함께 사라진다
추가 비용0에 가까움 (기존 구독 안에서 처리, 서버·DB 없는 정적 웹)0에 가까움 (AI 호출 없음, 학교 PC에서 원클릭 실행)
교사의 조작안내문 복사 → 붙여넣기 한 번. CLI·MCP를 몰라도 설치·연결은 에이전트가 스스로 함엑셀 파일 끌어다 놓기 → 점검
데이터 흐름PDF 파일은 이 앱의 서버로 업로드되지 않음. 단 선택한 쪽의 텍스트·이미지는 에이전트를 거쳐 구독 AI 회사로 전달됨실명·원본은 브라우저 밖으로 나가지 않음, 서버는 익명 정보만 받음
  • 슬라이드 제작(보강): 로컬 CLI를 직접 호출하던 구조를, CLI와 MCP를 모르는 선생님도 쓸 수 있게 웹 → 로컬 직접 소통으로 바꿨다. 선생님이 쓰는 Claude, ChatGPT, Gemini, Codex, Antigravity 등 어떤 AI 에이전트라도 쉽고, 매우 빠르고, 별도의 조작 없이 교재 PDF로 수업 슬라이드를 만든다. 도입 당일부터 쓸 수 있다.
  • 생활기록부 점검(열화): API를 완전히 제거하고(여유가 생기면 원격 MCP 구조 도입 검토), 오류 판독 수준이던 기계적 점검을 API 수준에 가깝게 끌어올렸다. 그래서 어떤 선생님이라도 제로에 가까운 비용으로 학교 전 학년을 한 번에 점검할 수 있다.

1부. 수업 교재 슬라이드 자동 제작

3. 개요

3.1 배경

  • 교사는 교재 PDF의 몇 쪽을 수업용 슬라이드로 옮기는 데 많은 시간을 쓴다. 본문 옮겨 적기, 그림 잘라 붙이기, 레이아웃 맞추기가 매 차시 반복된다.
  • 기존 도구는 PDF 선택 범위를 HTML 슬라이드로 만드는 로컬 데스크톱 앱이었다. 사용량이 충분한 로컬 CLI를 앱이 직접 호출해 작업을 지시하고 바로 결과를 받았다. 빠르고 강력했지만, 특정 컴퓨터의 설치 경로·결과물 폴더·터미널 실행 환경에 묶여 있었다.
  • 무엇보다 선생님들은 CLI를 잘 모르고, MCP 같은 연결 방식도 모른다. 그래서 웹 페이지가 로컬 에이전트와 직접 소통하는 방법을 새로 만들었다(§5).
  • 한편 많은 교사가 이미 AI 서비스를 개인 구독하고 있다. 이미 내고 있는 구독을 그대로 쓰면 추가 비용이 없다.

3.2 목표

  • 웹 페이지 하나에서 PDF를 열고, 필요한 쪽만 고르고, 탬플릿을 정하면 선생님의 AI 에이전트가 슬라이드를 만들어 제출한다.
  • 어떤 에이전트든 연결된다. 명령을 실행할 수 있는 에이전트(CLI·로컬 AI 앱), 브라우저 화면을 읽는 에이전트, 웹 채팅만 쓰는 경우까지 모두 지원한다.
  • 교사의 조작은 안내문 복사 → 에이전트 대화창에 붙여넣기 한 번이다. 준비, 연결, 작업 읽기, 제출은 에이전트가 스스로 한다.
  • PDF 파일은 이 앱의 서버로 업로드하지 않는다. 렌더링, 텍스트 추출, 이미지 자르기, 최종 패키징 모두 브라우저에서 한다. 단 선택한 쪽의 텍스트와 에이전트가 요청한 쪽 이미지는 에이전트를 거쳐 선생님이 구독하는 AI 회사로 전달된다.
  • 결과는 오프라인에서도 열리는 단일 HTML 파일이다.

3.3 대상 사용자

  • 교재 PDF로 수업 자료를 만드는 모든 교과 교사(특히 외국어·한자 교과)
  • AI 서비스를 개인 구독하고 있으나 API·설치에 익숙하지 않은 교사

3.4 범위 밖

  • 서버 측 PDF 처리·저장
  • 유료 API를 앱이 직접 호출하는 방식
  • 원격 MCP(웹 AI 커넥터): 서비스별 요금제·지역·기술 제한이 커서 보류(§7.4)
  • 계정·결제 기능(현재는 로그인 없는 정적 웹 도구, 인증은 교체 지점만 둠)

4. 사용자 흐름

  1. PDF 열기: 교재 PDF를 연다. 브라우저 안에서만 처리된다는 표시가 함께 보인다.
  2. 쪽 고르기: 썸네일에서 필요한 쪽만 고른다. 처음에는 아무 쪽도 선택되지 않으며, 전체 선택은 비용 때문에 제공하지 않는다. 쪽 번호로 바로 이동할 수 있다.
  3. 설정: 신규 생성이면 파일명·탬플릿·디자인 지시를, 수정이면 기존 결과물과 수정 지시를 정한다. 입력 즉시 자동 저장된다.
  4. 도우미 연결: "도우미에게 보낼 내용 복사"를 누르고, 쓰고 있는 AI 에이전트 대화창에 붙여넣는다. 승인 창이 뜨면 허용만 누른다.
  5. 자동 제작: 에이전트가 작업 지시서와 선택 쪽의 텍스트를 읽고, 필요한 쪽만 이미지를 받아 보고, 슬라이드 HTML을 제출한다.
  6. 미리보기·내려받기: 브라우저가 런타임·서체·필순·잘라낸 그림을 넣어 단일 HTML로 묶고 미리보기에 띄운다. 결과물을 내려받는다.
  7. 수정: 수정 지시를 쓰고 같은 단추로 복사해 같은 대화창에 붙여넣으면, 에이전트가 새 작업을 읽고 고쳐서 다시 제출한다.

5. 에이전트 연결 구조 — "어떤 에이전트라도"

5.1 세 가지 통로

에이전트 유형통로교사의 조작
명령을 실행할 수 있는 에이전트 (Claude Code, Codex, Antigravity 등 CLI·로컬 AI 앱)로컬 브리지 — 에이전트 쪽은 명령어 또는 MCP, 브라우저 쪽은 이 컴퓨터 안의 로컬 연결안내문 붙여넣기 1회
브라우저 화면을 보는 에이전트읽기 쉬운 화면 — "에이전트 작업" 보기에 지시서·페이지별 텍스트·제출 칸, 기계 판독용 상태 JSON화면을 맡기기만 함
웹 채팅만 쓰는 경우 (ChatGPT·Claude·Gemini 웹)작업 문서 — 작업 문서를 내려받아 채팅에 첨부, 답변을 통째로 붙여넣으면 HTML 부분만 찾아 패키징첨부 1회 + 붙여넣기 1회
  • 조작 기능은 도구 목록 하나로 정의하고 모든 통로가 함께 쓴다: 상태 읽기, 탬플릿 목록, 쪽 범위 선택, 옵션 변경, 작업 만들기·읽기, 페이지 이미지, 결과물 목록·읽기, 결과 제출.
  • MCP 등록 없이도 동작한다. 원하면 한 번 연결한 뒤 MCP 도구로 등록할 수 있다.

5.2 완전 자동 준비 — 교사는 Node.js·폴더·포트를 몰라도 된다

  • 안내문의 첫 줄은 운영체제별 준비 한 줄이다. 에이전트가 이를 실행하면:
    1. 실행 환경(Node.js)이 없으면 공식 배포처에서 휴대용 버전을 사용자 폴더에 받는다. 해시로 검증하고, 관리자 권한이 필요 없으며, 시스템을 바꾸지 않는다.
    2. 브리지(의존성까지 묶은 한 파일)를 이 페이지 주소에서 받는다. 페이지 버전과 같은 브리지가 보장된다.
    3. 실행 파일을 만들고 준비 완료를 알린다.
  • 다음 준비 때는 받아 둔 실행 환경을 재사용한다.

5.3 역방향 연결 — 페이지가 열쇠를 만든다

  • 페이지가 탭마다 128비트 접속 키와 무작위 포트 후보 3개를 만들어 안내문에 넣는다. 교사가 번호를 입력하거나 포트를 고를 일이 없다.
  • 브리지는 후보 중 첫 빈 포트에서 열리고, 페이지는 후보를 돌아가며 시도한다. 응답 없는 포트는 제한 시간 뒤 건너뛴다.
  • 브리지가 재시작되어도 보관한 키로 다시 열고 페이지가 자동 재연결한다. 모두 실패하면 "연결 새로 만들기"로 새 키·새 포트를 만든다.

5.4 브라우저별 대응

  • Chrome·Edge: 인터넷 페이지가 이 컴퓨터에 연결하려면 "로컬 네트워크 접근" 허용이 필요하다. 복사 단추를 누르는 순간 허용 창을 유도하고, 거부 상태면 허용 방법을 안내한다.
  • Safari: 보안 규칙상 https 페이지에서 로컬 연결이 구조적으로 막힌다. 그래서 연결 창(중계 창) 방식을 두었다. 단추 한 번으로 지시서 복사와 연결 창 열기를 함께 하고, 연결 창이 원래 페이지와 브리지 사이를 이어 준다.

6. 탬플릿과 패키징

6.1 탬플릿

탬플릿내용
중국어 탬플릿단어·문장·복습 슬라이드 자동 구성, 한자 필순 재생, 병음·뜻 가리기
범용 클래식 슬라이드어떤 교과에나 쓰는 16:9 발표 슬라이드. 레이아웃 11종, 색 조합 5종
커스텀교사의 직접 지시로 자유 구성
  • 에이전트는 내용만 채운다. 정해진 마크업에 글과 그림 위치만 넣고 CSS·JS는 쓰지 않는다. 디자인·런타임·서체·필순은 브라우저 패키저가 붙이므로 토큰이 들지 않고 결과 품질이 고르다.
  • 넘치는 슬라이드는 글자를 자동으로 줄여 맞추고, 인쇄·PDF 저장 시 슬라이드 한 장이 한 쪽이 된다. JS가 꺼져 있어도 내용이 보인다.

6.2 브라우저 패키저

  • 기존 Python 패키징을 브라우저 TypeScript로 다시 구현했다. 서버가 필요 없다.
  • 그림은 원본 쪽 번호 + 자르기 영역으로만 표기하면, 패키저가 PDF에서 그 영역을 잘라 넣는다. 에이전트가 이미지를 다시 만들 필요가 없다.
  • 서체는 문서에 쓰인 글자가 든 묶음만, 필순 데이터는 쓰인 한자만 넣는다.
  • 결과는 런타임·서체·필순·그림·보안 정책·라이선스 고지가 모두 들어 있는 단일 HTML이다.

6.3 결과 HTML 자체 편집

  • 내려받은 결과 HTML 안에 편집 단추가 있다. 글자를 그 자리에서 고치고 저장하면 편집본 HTML을 내려받는다. AI 없이도 마지막 손질을 할 수 있다.
  • 런타임이 만든 화면은 편집본에 섞이지 않게 원본 문서를 따로 보관해 두고 고친 글자만 옮겨 넣는다.

7. 비용·개인정보·보안

7.1 비용 원칙

  • 선택한 쪽만, 텍스트 먼저, 이미지는 필요할 때만 에이전트에게 준다. 전체 선택을 없앤 이유다.
  • 디자인 요소는 패키저가 붙이므로 에이전트의 출력은 내용 HTML뿐이다.
  • 앱 자체는 서버·DB 없는 정적 웹이라 운영비가 거의 없다.

7.2 PDF 비업로드 실측

시험결과

7.4 원격 MCP를 보류한 이유

  • 웹 AI 채팅이 공개 서버의 도구를 직접 부르는 방식은 서비스마다 요금제(무료 불가·쓰기 제한), 지역(국내 사용 불가), 중계 서버 필요, 메시지 크기 제한이 있었다.
  • "어떤 선생님이라도, 추가 비용 없이"라는 취지에 맞지 않아, 모든 요금제에서 되는 로컬 브리지 + 읽기 쉬운 화면 + 작업 문서 세 통로를 기본으로 정했다.

8. 화면·이식성

  • 다국어: 화면 23개 언어, 오른쪽→왼쪽 언어 지원. 결과 HTML의 조작부도 23개 언어를 담아 혼자 열려도 해당 언어로 보인다. 에이전트에게는 사용자 화면 언어로 답하라고 알린다.
  • 상대 경로: 모든 리소스를 상대 경로와 문서 기준 주소로 불러, 상위 사이트 어느 하위 경로에 붙여도 동작한다. 시험 서버를 일부러 깊은 하위 경로에 올려 매번 확인한다.
  • 내용 해시 버전: 손으로 올리는 버전 번호 없이, 원본 내용 해시가 정적 리소스 경로가 된다. 원본이 그대로면 같은 경로라 캐시를 쓰고, 바뀌면 새 경로로 받는다. 에이전트가 연결 중이면 새로고침을 미루고 안내만 띄운다.
  • 브라우저 임시 저장: 설정·결과물·마지막 PDF를 IndexedDB에 둬 새로고침해도 이어서 작업한다.
  • 인증 교체 지점: 로그인 화면이 없고, 상위 서비스 인증으로 바꿀 지점을 한 곳에 모았다.

9. 처리 구조와 성능

  • PDF 처리: pdf.js로 렌더링·텍스트 추출·쪽 추출. 일부 PDF 글꼴이 한자를 부수 코드로 추출하는 문제는 해당 영역만 일반 한자로 정규화한다.
  • 썸네일: 보이는 쪽부터 동시에 2장씩 렌더링한다. 우선순위는 이동한 쪽 → 화면에 보이는 쪽 → 나머지 순서. 다른 묶음으로 넘어가면 이전 대기 작업을 취소한다. 앱 시작 후 한가할 때 pdf.js를 미리 받아 둔다.

11. 검증

  • 타입 검사·빌드 통과, 하위 경로 배치에서 모든 리소스 정상 로드, 페이지 콘솔 오류 0건
  • 실제 MCP 클라이언트로 전 도구 동작: 틀린 키 거부, 맞는 키 연결, 페이지 이미지·결과 제출·미리보기
  • 패키저: 외부 스크립트가 든 HTML 거부, 정상 HTML은 단일 파일로 패키징
  • 실행 환경이 없는 PC 재현: 실행 경로에서 Node.js를 모두 뺀 상태로 안내문 그대로 준비 → 연결 → 작업 → 이미지 → 제출 → MCP 모드까지 성공
  • 장애 상황: 첫 포트를 다른 프로그램이 점유, 응답 없는 프로그램이 포트 점유, 브리지 강제 종료 후 제출 — 모두 자동 회피·재연결
  • 브라우저: Chrome 직접 연결, WebKit(Safari) 연결 창 경유 연결, 실제 Mac Safari에서 지연·세 번째 후보 포트 조건으로 확인
  • 탬플릿: 범용 클래식 11개 레이아웃 넘침 없음, 과부하 슬라이드 자동 축소, 인쇄 쪽 수 일치, JS 끔 상태 표시

12. 향후 과제 (1부)

  • 실제 교재 PDF로 교과별 생성 품질 확인과 탬플릿 추가
  • Windows 준비 스크립트 실기 확인

2부. 학교생활기록부 자동 점검

2026-11-22 제출본을 옮기고 장 번호를 이어 붙였다. 핵심 결정은 API를 완전히 제거하고, 오류 판독 수준이던 기계적 점검을 API 수준에 가깝게 끌어올린 것이다.

13. 개요

13.1 배경

  • 학교생활기록부는 해마다 바뀌는 기재요령 지침을 지켜야 하며, 학기 말마다 교사가 많은 기록을 직접 대조·점검한다.
  • 기존 도구는 엑셀 자동화가 거의 갖춰져 있었지만 판정은 외부 AI API 중심이었다. 기계적 점검은 오류를 판독하는 수준에 그쳤고, API 호출 비용과 개인정보 유출 위험이 컸다.
  • 이번에는 API를 완전히 제거하고, 지침 대조 규칙을 촘촘히 늘려 기계적 점검을 API 수준에 가깝게 끌어올렸다.
  • 학생 기록은 가장 민감한 개인정보다. 그래서 "서버를 믿어 달라"가 아니라 "서버가 알 수 없게 설계했다"를 증명할 수 있어야 한다.

13.2 목표

  • NEIS에서 내려받은 생활기록부 엑셀 파일을 넣으면 지침 위반·주의 사항을 코드로 자동 판정한다.
  • 개인정보는 브라우저 밖으로 나가지 않는다. 서버는 익명화된 정보만 받고, 실명으로 되돌리는 키는 사용자만 가진다.
  • 한 학교 전 학년(약 2,000명 이상)을 한 번에, 여러 사용자가 동시에 점검한다.
  • 원클릭 독립 실행과 기존 웹사이트 하위 페이지로의 이식을 같은 코드로 지원한다.

13.3 대상 사용자

  • 고등학교 담임·교과 교사, 생활기록부 점검 담당자
  • 학교·교육 플랫폼 운영자(자기 사이트에 이 기능을 붙여 제공)

13.4 범위 밖

  • AI 기반 점검(문맥, 허위·과장 판단, AI 생성 여부 등 판단이 필요한 항목)
  • 맞춤법 검사(외부 API 미사용 원칙)
  • 결제·신청·승인 등 운영 기능
  • 다중 서버 수평 확장(설계상 경로만 문서화)

14. 핵심 설계 원칙

원칙내용
AI 호출 없음모든 판정은 결정적(deterministic) 규칙 코드로만 한다. 같은 입력은 언제나 같은 결과이고, 호출 비용과 외부 전송이 없다
영지식에 가까운 서버서버는 실명, 원본 파일, 토큰 대응표를 받지 않는다. 서버 DB가 통째로 유출되어도 학생을 특정할 수 없다
다층 방어브라우저 형식 검사 → 브라우저 익명화 → 사용자 확인 → 서버 잔여 개인정보 재검사 → 저장 시 서버 암호화
근거 추적모든 판정은 규칙 ID, 수준, 근거(지침 연도·항목)를 함께 가진다
지침 버전 관리규칙 세트를 학교급 × 적용 시작 학년도로 관리하고, 기록마다 맞는 세트를 자동 선택한다
무가정 이식성상위 사이트의 경로·인증·도메인을 가정하지 않는다. 절대 경로 하드코딩과 자체 로그인 화면이 없다
완전한 독립성앱 폴더 하나에 코드, 벤더 라이브러리, 규칙 데이터, 실행기, 컨테이너 구성이 모두 들어 있다. 외부 CDN이나 다른 저장소를 참조하지 않는다

15. 사용자 흐름

  1. 파일 넣기: NEIS 항목별 조회에서 내려받은 .xlsx 파일(학적·출결·수상·봉사·창체·세특·독서·행특)을 끌어다 놓는다.
  2. 자동 인식: 브라우저가 파일마다 형식을 검사하고, 항목·학교·학년·반·학생을 판별한다. 파일 지문(SHA-256)도 이때 계산한다.
  3. 설정: 학교별로 요일별 수업 교시, 학사 일정, 교육계획서 수상명, 사용자 검사어(이유 포함) 등을 정한다. 기준 학년도는 파일의 날짜에서 추정해 채운다.
  4. 익명화 확인: 학생 이름, 학교명, 연락처 등 식별 정보를 토큰으로 바꾼 결과를 미리 보고 확인한다.
  5. 복원 키 내려받기: 이름을 되돌릴 수 있는 복원 파일을 사용자가 보관한다. 서버는 이 키를 모른다.
  6. 보관 동의(선택): 결과와 복원 정보를 이 브라우저에 보관할지 고른다.
  7. 점검: 익명화된 데이터만 압축해 서버로 보내고, 진행률을 확인한다.
  8. 결과 확인: 학생별·영역별로 판정을 보고, 복원 키가 있으면 실명으로 표시한다. 판정마다 "확인함" 체크를 남긴다.

                                  익명화 셀 JSON(gzip) ──────────▶ 재검사 ─▶ 규칙 엔진
  • 원본 파일 바이트, 실명, 대응표는 어느 단계에서도 네트워크로 나가지 않는다.
  • 서버가 받는 것은 셀 좌표와 익명화된 텍스트, 비개인 설정, 파일 지문뿐이다.

16.2 토큰 방식

  • 식별 정보를 ⟦종류:무작위ID⟧ 형식의 토큰으로 바꾼다. ID는 UUIDv4라서 원문을 추측할 수 없다.
  • 토큰 종류: 학생, 인물, 학교, 지역, 기관, 연락처, 식별정보, 사용자 검사어
  • 치환 규칙:
    • 유니코드 NFC 정규화를 먼저 한다. 자모가 분리된(NFD) 문자열이 치환을 빠져나가지 못하게 한다.
    • 긴 문자열부터 한 번만 치환한다. "별빛고등학교"가 "별빛"보다 먼저 바뀌어 부분 치환·이중 치환이 생기지 않는다.
    • 학교명은 엑셀 머리·바닥글에서 자동으로 찾고, 줄임말(…고·…중·…초)까지 함께 익명화한다.
  • 토큰이어도 점검은 된다: 서버는 토큰의 종류와 출현 위치만으로 "기록에 학교명이 들어 있다", "사용자 검사어가 나왔다" 같은 판정을 한다. 원문을 알 필요가 없다.
  • 사용자 검사어는 원문과 이유 모두 서버로 보내지 않는다. 토큰만 보내고, 이유는 복원 파일 안에만 남는다.

16.3 복원 키

  • 복원 파일 = 대응표 암호문 + 키. 파일 자체가 키이므로 서버에는 키 사본이 없다.
  • 암호화: 32바이트 무작위 비밀값 → PBKDF2 키 유도 → AES-GCM-256 인증 암호화
  • 복원 키가 없으면 결과는 학생 1, ○○1고등학교 같은 별칭으로 보인다. 화면이 가려지면 실명 표시를 다시 가린다.
  • 분실 시 복구할 수 없다는 안내를 흐름 곳곳에서 반복해 보인다.

16.4 브라우저 보관

  • 동의한 경우에만 IndexedDB에 보관한다. 기본값은 "보관 안 함"이며 작업마다 다시 묻는다.
  • 복원 키는 **추출 불가(non-extractable) CryptoKey**로 보관한다. 스크립트도 키 원본을 읽을 수 없고, 암·복호화 연산만 요청할 수 있다.
  • 계정별로 보관소를 분리하고, 보관 개수 상한을 넘으면 알린 뒤 오래된 것부터 지운다.

17. 보안 설계

17.2 웹 보안

  • CSRF: 상태를 바꾸는 모든 요청에 페이지가 발급한 사용자 정의 헤더와 Origin/Referer 동일 출처 확인을 함께 요구한다.
  • CSP: default-src 'self', 인라인 스크립트 금지, 외부 CDN 없음. 삽입 가능한 상위 사이트(frame-ancestors)는 설정으로 정한다.
  • XSS 차단: 사용자 데이터는 모두 textContent로만 화면에 넣는다. HTML로 해석되는 경로가 없다.
  • 원문 전송 차단: 원문을 다루는 화면 요소는 "로컬 전용"으로 표시하고, htmx 요청 단계에서 서버 전송을 원천 차단한다.
  • 세션: 서버가 무작위 세션 쿠키를 발급한다(HttpOnly, SameSite=Lax, 앱 경로로 범위 제한, 운영 환경 Secure).
  • 보안 컨텍스트: 암호 기능은 HTTPS 또는 localhost에서만 동작하는 WebCrypto를 쓴다.

17.3 서버 저장 데이터

데이터저장 방식
계정 식별상위 시스템의 계정 ID 원문 대신 비밀키 HMAC 값만 저장
파일 지문브라우저의 SHA-256을 서버가 비밀키 HMAC으로 다시 감싸 저장. 원본 해시가 남지 않고, 계정 사이에 같은 파일인지 연결할 수도 없다. 재점검 횟수만 센다
작업량파일 수, 학생 수, 기록 수, 판정 수, 처리 시간 등 숫자 집계만
결과(선택)운영 정책 스위치가 켜졌을 때만, 이미 익명화된 결과를 AES-256-GCM으로 한 번 더 암호화. 계정·작업·형식을 AAD로 묶어 다른 행에 옮겨 붙이면 복호화가 실패한다. 키 버전 열로 키 교체를 지원
  • 서버 로그에는 작업 ID와 건수만 남긴다. 셀 내용, 토큰 대응, 검사어는 남기지 않는다.
  • 저장 스위치가 꺼지면 결과 테이블은 쓰지도 읽지도 않고, 화면 안내문도 자동으로 바뀐다.

17.4 공급망

  • Python 의존성은 하위 의존성까지 버전과 해시를 고정하고, 해시가 다르면 설치를 거부한다.
  • 설치 때마다 알려진 취약점 점검과 의존성 충돌 점검을 한다.
  • 화면 라이브러리(htmx, SheetJS, 텍스트 레이아웃 엔진)는 버전을 고정해 앱 안에 직접 포함했다(SheetJS는 복사 시 해시 검증). 런타임에 외부에서 받지 않는다.

18. 이식성

18.1 인증 상속

  • 앱의 모든 경로(페이지, API, 부분화면, 정적 파일까지)를 인증 의존성 하나가 걸린 단일 루트 라우터 아래에 둔다. 경로 하나를 빠뜨려 인증 없이 열리는 일이 구조적으로 생기지 않는다.
  • 인증은 어댑터로 분리했다. 이식할 때는 다음 중 하나로 교체한다.
    • 상위 앱의 인증 의존성을 라우터 생성 함수에 그대로 넘긴다.
    • 공유 비밀과 함께 신뢰하는 프록시 헤더를 쓴다.
  • 앱은 로그인 화면을 만들지 않는다. 상위 사이트의 로그인을 그대로 쓴다.

18.2 경로 독립

  • 다음 세 가지 배치를 모두 지원한다.
    1. 설정으로 상위 경로를 지정
    2. 상위 웹 앱이 이 앱을 하위 경로에 마운트(경로 자동 인식)
    3. 리버스 프록시가 넘기는 접두 경로 헤더(명시적으로 신뢰할 때만)
  • 서버 템플릿의 링크와 브라우저의 fetch, Worker, 동적 import, htmx 요청이 모두 하나의 URL 도우미를 거친다. 쿠키 범위와 리다이렉트도 같은 상위 경로를 따른다.

18.3 버전 경로와 캐시

  • 정적 파일 경로에 앱 버전을 넣고, 1년 불변(immutable) 캐시를 준다. 버전을 올리면 모든 리소스가 새 경로로 받아진다.
  • 쿼리스트링 방식과 달리, 라이브러리 내부의 상대 import까지 같은 버전 경로를 타서 캐시 무효화가 끝까지 전파된다.
  • HTML과 부분화면은 캐시하지 않는다. 화면이 다시 보일 때 버전을 확인해, 바뀌었으면 새로고침 안내를 띄운다(작업 중 강제 새로고침은 하지 않음).

18.4 데이터 격리

  • DB 테이블을 전용 스키마에 둔다. 기존 공용 DB에 붙여도 테이블 이름이 겹치지 않는다.
  • 스키마 변경은 시작 시 자동 마이그레이션하며, 여러 인스턴스가 동시에 시작해도 DB 잠금으로 한 번만 적용된다.

19. 독립 실행과 격리

19.1 원클릭 실행

  • macOS·Windows·Linux용 실행기를 셸과 PowerShell로만 작성했다. 호스트에 Python이 없어도 된다.
  • 실행기가 하는 일:
    1. 설치된 컨테이너 CLI와 Compose를 여러 경로에서 찾는다(Docker Desktop, OrbStack, Colima, Rancher Desktop, Podman).
    2. 엔진이 꺼져 있으면 다른 컨텍스트를 시험하고, 그래도 안 되면 설치된 런타임을 직접 기동한다. 끝내 실패하면 무엇을 설치·실행해야 하는지 안내한다.
    3. 첫 실행 때 설정 파일과 무작위 DB 비밀번호, 영구 저장 폴더를 만든다.
    4. 사용 중인 포트를 피해 빈 포트를 고른다.
    5. 앱과 DB를 빌드·기동하고, 상태 확인(healthcheck)을 통과하면 브라우저를 연다.
    6. 앱이 끝나면 컨테이너를 내린다. 데이터는 유지한다. Ctrl+C나 창 닫기도 같은 정리 절차를 탄다.

19.2 컨테이너 격리

항목설계
이름고유한 Compose 프로젝트 이름. 같은 PC의 다른 서비스와 컨테이너·네트워크·볼륨 이름이 겹치지 않는다
네트워크앱과 DB만 쓰는 전용 네트워크. DB는 기본적으로 호스트에 포트를 열지 않는다(포트 충돌·외부 접근 가능성 0)
앱 포트기본적으로 127.0.0.1에만 묶는다
권한비루트 사용자로 실행. 컨테이너 안에 도커 소켓을 넣지 않는다
규칙 데이터읽기 전용으로 마운트하며, 웹 경로로 노출하지 않는다
영구 데이터DB 데이터와 서버 키를 앱 폴더의 전용 저장소에 둔다. 저장소 안에 자체 제외 규칙을 두어 버전 관리에 실수로 올라가지 않는다. Windows 권한 문제를 피하는 명명 볼륨 모드도 있다
재시작자동 재시작 없음. 종료 후 스스로 다시 뜨지 않는다
기동 순서DB 상태 확인을 통과해야 앱이 뜬다
아키텍처멀티아키텍처 베이스 이미지를 로컬 빌드하여 Apple Silicon(arm64)과 x86(amd64)에서 모두 동작
재현성로컬 개발 환경과 컨테이너가 같은 Python 버전과 같은 고정 의존성 목록을 공유

19.3 페이지 닫힘 자동 종료

  • 브라우저는 주기적으로 생존 신호를 보내고, 페이지를 떠날 때 종료 신호(sendBeacon)를 보낸다. 탭마다 ID를 둬서 여러 탭을 센다.
  • 서버는 다음 조건으로 정상 종료한다.
    • 마지막 탭이 떠난 뒤 유예 시간 안에 새 신호가 없을 때(새로고침은 버팀)
    • 생존 신호가 일정 시간 없을 때(백그라운드 탭의 타이머 지연을 고려한 값)
    • 단, 시작 직후 유예 시간 동안과 처리 중인 작업이 있을 때는 미룬다.
  • 이 기능은 독립 실행 때만 켜진다. 다른 사이트에 이식하면 기본적으로 꺼져 있다.

19.4 작업 격리

  • 작업은 (계정, 세션) 단위로 격리한다. 다른 계정·세션의 작업 ID로 접근하면 존재 여부도 알리지 않고 404를 준다.
  • 결과는 한 번 받아 가면 서버 메모리에서 지운다. 받아 가지 않은 결과도 정해진 시간이 지나면 지운다.

문자 점검AI 생성 글에 흔한, 키보드로 치기 어려운 문자(변형 따옴표·쉼표·마침표, 보이지 않는 문자, 방향 제어 문자, 특수 공백, 전각 문자, 자모 분리 흔적 등)를 코드포인트와 권장 대체로 표시
  • 판정 수준은 위반 / 주의 / 정보 3단계다.
  • 규칙 세트 선택: 기록의 학교급(학교명 끝으로 판별)과 학년도를 보고, 같은 학교급에서 적용 시작 학년도 ≤ 기록 학년도인 세트 중 가장 최근 것을 영역별로 고른다. 새 지침이 나오면 바뀐 영역만 새 세트로 추가하면 된다.
  • 학년도 추론: 날짜가 없는 기록(출결·창체·세특·행특)은 같은 학생의 날짜 근거(수상·봉사 날짜, 독서 학년도)로 "기록학년 → 학년도"를 추론한다. 기준 학년도를 잘못 넣어도 판정이 흔들리지 않고, 진짜 날짜 오기만 잡는다.
  • 정본 원칙: 최신 지침을 정본으로 지정하고, 정본과 어긋나는 기존 규칙은 지우지 않고 데이터 파일에서 끄며 근거를 남긴다.
  • 규칙 기준값과 키워드는 코드와 분리된 데이터 파일로 관리하며, 파일을 고치면 재빌드 없이 다음 작업부터 반영된다(외부 비공개).

21. 처리 구조와 성능

  • 서버 처리: 웹 서버는 단일 프로세스로 메모리 작업 저장소를 공유하고, CPU 작업은 프로세스 풀로 보내 GIL을 피해 병렬 처리한다.
  • 규칙 실행: 기록 단위 규칙은 순수 함수로 짜서 병렬화하고, 학생 간 비교 규칙(개근 통계, 중복 문장)만 작업 단위로 실행한다.
  • 키워드 검색: 모든 키워드를 긴 말 우선 대안으로 합친 정규식 하나로 미리 컴파일해, 본문을 한 번만 훑는다(본문 길이에 비례).
  • 동시성 제어: 전역 동시 작업 수와 계정당 동시 작업 수를 제한하고, 넘으면 대기 순번을 보인다.
  • 전송: 브라우저 표준 CompressionStream으로 gzip 압축해 보낸다. Worker 간에는 Transferable로 복사 없이 넘긴다.

23. 검증

  • 자동 테스트(pytest): 심어 둔 문제 21종 검출, 규칙 세트 선택, 학년도 추론, 미익명화 데이터 거부, 계정·세션 격리, CSRF, 하위 경로 배치, 상위 앱 마운트, 정적 파일 포함 미인증 차단
  • 헤드리스 브라우저 전체 흐름: 파일 → 설정 → 익명화 → 복원 키 → 점검 → 결과 → 새로고침 후 재방문·실명 복원. 콘솔 오류와 CSP 위반 0건
  • 컨테이너 검증: 기존 DB 서비스와 충돌 없이 기동, 페이지 닫힘 자동 종료와 정리, 재실행 후 데이터 유지
  • DB 내용 검증: 계정 HMAC, 파일 지문 HMAC, 숫자 집계, 암호화 결과 외에는 아무것도 없음을 확인
  • 모든 시연·시험 자료는 가명 합성 데이터만 쓴다. 합성 NEIS 형식 파일 생성기를 함께 둔다.

23.1 보안·개인정보 점검표

  • 원본 파일 바이트와 실명 대응표가 네트워크로 나가지 않는가
  • 서버 잔여 개인정보 재검사가 동작하는가
  • 서버 로그에 셀 내용이 남지 않는가
  • 저장 OFF에서 DB에 지문·집계 외에 아무것도 남지 않는가
  • 다른 계정·세션의 작업과 결과에 접근할 수 없는가
  • CSP 위반 없이 동작하는가
  • 압축 폭탄, 거대 JSON, 매크로 파일, .xlsx가 아닌 파일을 거부하는가
  • 규칙 데이터와 영구 저장소가 웹 경로로 노출되지 않는가
