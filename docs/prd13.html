소크라테스 학습정리 PRD

수업이 끝날 때 학생이 AI와 문답하며 오늘 배운 것을 스스로 점검하는 웹 앱입니다.

0. 주의사항

  • 작업 순서는 15장 "하루 작업 순서"를 따릅니다. 각 단계는 테스트가 통과해야 끝난 것입니다.
  • 교사(사용자)가 직접 하는 일과 에이전트가 하면 안 되는 일이 있습니다(3장).
    • API 키는 교사가 앱의 [설정]에 직접 넣습니다. 채팅에 붙여 넣게 하지 않습니다.
    • 커밋과 푸시는 교사가 말할 때만 합니다.
    • 교사에게 묻고 보고할 때는 쉬운 한국어 존댓말을 씁니다.
  • "왜"가 적힌 규칙은 AI가 흔히 어기는 곳을 막는 규칙입니다. 빼거나 느슨하게 하지 않습니다.
  • 응답 칸(10~12장 표), 검사기 예문(9.3), 실제 AI 점검 기대값(16.3)은 이 문서가 정한 값입니다. 에이전트가 바꾸지 않습니다.
  • 시스템 프롬프트는 각 장의 "프롬프트에 넣을 규칙"과 "안 됨" 예를 모두 담아 에이전트가 씁니다.
  • 하루에 다 못 할 수 있습니다. 15장의 반드시(Must) 범위를 먼저 끝내고, 남으면(Should) 범위로 넘어갑니다.

1. 왜 만드는가

  • 문제
    • 수업이 끝나면 교사는 "학생들이 오늘 배운 것을 정말 이해했을까?"가 궁금합니다.
    • 정리 활동이 "배운 것 말하기"에서 끝나면, 잘못 이해한 부분(오개념)이 확인되지 않은 채 넘어갑니다.
    • 학생마다 되물어 볼 시간은 없습니다.
  • 출발점
    • 소크라테스식 대화로 평가한다는 생각("소크라테스트")에서 출발합니다.
    • 원래는 소크라테스만큼 아는 사람이 학생 수만큼 있어야 합니다. 그 역할을 AI가 맡습니다.
  • 핵심
    • AI는 답을 주지 않습니다.
    • 반례와 되묻기로, 학생이 모르던 것을 스스로 꺼내 알게 합니다.
  • 효과를 보는 기준
    • 학생 성취 점수가 아니라 두 가지로 봅니다.
      • 교사가 직접 되묻는 부담이 줄었는가
      • 학생이 오개념을 스스로 고쳤는가

2. 사용자와 사용 장면

항목내용
대상초등 5학년 2학기 사회, 3단원 「식민 통치와 저항, 전쟁이 바꾼 사회와 생활」
사용자교사(조작), 학생(말하기·쓰기)
장면수업 끝 5~7분. 교실 TV에 띄운 교사 PC 크롬에서 학생 1명씩 합니다. 한 차시에 보통 3명 정도가 이어서 합니다
입력학생이 교사 PC에 직접 치거나, 교사가 받아 적습니다
결과화면에 남는 정리와 표시. 복사하거나 A4 한 장으로 인쇄합니다. 저장하지 않습니다

목표

  1. 학생 1명이 2~5분 안에 끝납니다.
  2. AI의 질문과 판단은 고른 교과서의 "오늘까지 배운 차시" 내용 안에서만 나옵니다.
  3. 같은 차시에서 학생 여러 명이 이어서 해도 같은 문제가 되풀이되지 않습니다.
  4. 결과에 교사가 바로 설명할 수 있는 도움말이 남습니다(교과서를 다시 펴지 않고).

비목표: 학생 로그인, 점수·평가 기록, 학생이 혼자 AI와 대화하는 기능, 전 과목 지원, 교사마다 서버로 API를 대신 불러 주는 기능.

실패로 보는 것 (동작해도 이러면 실패입니다)

  • AI가 정답을 알려 줌
  • 퀴즈처럼 이름·연도를 맞히게 함
  • 학생에게 틀렸다는 느낌을 줌
  • 교과서에 없는 지식으로 판단함

3. 절대 지킬 원칙 (모든 방법에 공통)

학생에게 보이는 말

  • AI는 정답이나 설명을 말하지 않습니다. "틀렸", "정답은", "오답" 같은 말을 쓰지 않습니다.
  • 학생이 잘못했다는 느낌을 주는 말을 쓰지 않습니다. 예: "허점을 찾았어요" 대신 "모르는 것을 알게 되었어요".
  • 화면에 빨간색, X 표시, 점수를 쓰지 않습니다.
  • 질문은 한 번에 하나, 한 문장, 40자 이내(30자 안팎 권장), "요?"로 끝나는 존댓말입니다.
  • 퀴즈를 내지 않습니다. 이름·연도·장소·숫자를 맞히게 하는 질문은 안 됩니다. 그 사실을 모르는 학생은 막다른 곳에 서기 때문입니다. 대신 학생 말이 맞다면 어떤 일이 생기는지 묻습니다.

판단의 근거

  • 고른 교과서의 개념·오개념, 오늘 차시 원문만 근거로 판단합니다. AI가 따로 아는 지식은 쓰지 않습니다.
  • 표현이 달라도 뜻이 같으면 맞는 것으로 봅니다. 맞춤법과 띄어쓰기는 문제 삼지 않습니다.

흐름과 검사

  • 흐름은 코드가, 글은 AI가 정합니다. 질문 수, 끝내는 때, 검사 실패 처리는 코드가 정합니다. AI는 정해진 JSON 하나만 돌려줍니다.

개인정보와 비밀

  • 학생 이름을 받지 않습니다. 대화는 메모리에만 있고, [다음 학생]을 누르면 사라집니다.
  • API 키는 코드·저장소·채팅에 넣지 않습니다. 교사가 [설정]에 넣고, 그 브라우저의 localStorage에만 둡니다.

저작권

  • 교과서 PDF와 거기서 뽑은 원문은 출판사 저작물입니다. git에 올리지 않고, 배포하지 않습니다(.gitignore로 막음).
  • 데이터에는 교과서 문장을 25자 이상 그대로 옮기지 않고 요약합니다. 테스트로 검사합니다.

5. 준비

설치할 것

  • Git, GitHub CLI(gh)
  • Node.js 20 이상: 테스트용입니다. 앱 자체는 빌드가 없습니다.
  • Python 3.11 이상 + pymupdf: PDF에서 글자를 뽑는 데 씁니다.
  • Claude Code

준비물

  • 천재교과서 5-2 사회 교과서 PDF(텍스트 레이어 있음). 작업 폴더 밖이나 textbook/(git 제외)에 둡니다.
  • Anthropic API 키. 교사가 앱 [설정]에 직접 넣습니다.
  • 교사가 미리 할 일
    • gh auth login으로 GitHub에 로그인합니다.
    • 빈 저장소를 하나 만듭니다. Pages를 쓰려면 공개 저장소여야 합니다(14장).
  • 점검용 브라우저
    • 실제 AI 점검(16.3)은 브라우저에서 돕니다. 키가 그 브라우저의 localStorage에 있어야 하기 때문입니다.
    • 아래 둘 중 하나를 씁니다.
      • Claude Code 데스크톱 앱의 내장 브라우저 창
      • npx playwright 창
    • 교사가 그 창에서 앱 [설정]에 키를 한 번 넣습니다. 에이전트는 키 값을 읽지 않고, 점검 페이지의 [실행]만 누릅니다.

Windows에서 알아 둘 것

  • 한글이 깨지면 Python은 python -X utf8로 실행합니다.
  • 셸 히어독에 한글이나 JS를 길게 넣으면 깨집니다. 스크립트는 파일로 써서 실행합니다.
  • 줄끝이 섞이면 정확히 바꾸기가 실패합니다. .gitattributes에 * text=auto eol=lf를 둡니다.

개발 서버

  • python -m http.server 8765 --directory app를 씁니다.
  • 앱은 ES 모듈 없이 일반 스크립트라 file://로도 열리지만, 점검 페이지 때문에 서버를 씁니다.

코드 모양

  • 모든 JS는 (function (root) { … })(this) 모양의 일반 스크립트입니다.
    • 브라우저에서는 window.Sok… 전역으로 씁니다(예: SokGuard, SokTopic, SokUI, SokParts, SokLLM).
    • Node 테스트에서는 module.exports로 씁니다.
  • 빌드 과정이 없습니다.
  • index.html 스크립트 순서: 데이터 → guard → topic → catalog → ui → parts → llm → 방법 흐름 → 방법 화면 → app.
  • local/texts.js는 <script src="local/texts.js" onerror="this.remove()">로 불러옵니다. 없으면 그냥 넘어갑니다.
  • 스크립트와 CSS에는 ?v=숫자를 붙입니다. 파일을 고치면 숫자를 올립니다. 올리지 않으면 브라우저가 옛 파일을 씁니다.

7.2 데이터 규칙 (테스트로 검사: data.test.js, detective-data.test.js)

개념과 오개념

  • 개념은 차시당 4~8개입니다. 교과서 문장을 요약하며, 25자 이상 같은 곳이 있으면 안 됩니다.
    • 이 검사는 app/local/texts.js(원문)가 있을 때만 돕니다.
    • 원문이 없는 곳(배포 환경, 다른 PC)에서는 실패가 아니라 건너뜀(skip)으로 표시합니다.
  • 오개념은 교과서의 확인 문제("○× 문제", "마무리하기")에 나오는 틀린 문장이나, 학생이 할 법한 착각에서 뽑습니다.
  • 차시마다 오개념 3~4개를 목표로 합니다. 학생 3명이 이어서 해도 문제가 겹치지 않으려면 필요합니다. 교과서 근거가 약하면 억지로 만들지 않고 2개로 둡니다.
  • counterHints
    • 2개 이상이고, 각각 40자 이내, "요?"로 끝나는 질문입니다.
    • 사실 묻기(퀴즈) 꼴이 아니어야 합니다(9.3의 isFactQuestion을 통과).
    • 정답을 품으면 안 됩니다. 예: "…중국군이 들어오자 어떻게…"는 안 됩니다.
  • sources의 차시와 쪽은 원문에서 확인한 것이어야 합니다.
  • 모든 항목이 reviewed: true여야 앱에서 씁니다.
  • 묶음을 합친 결과에 검사 오류가 0개여야 합니다(validateTopic(mergeTopics(...)) → []).

오답 탐정 문제

  • 오개념마다 2벌(a·b)을 만듭니다.
  • textbooks는 오개념 sources의 교과서 안에 있어야 합니다.
  • 문장은 4개이고, 각각 40자 이내, "요."로 끝납니다.
  • 숨은 위치(hidden)는 0~3에 고루 나뉘어야 합니다(위치마다 전체의 1/5 이상).
  • key는 한 줄의 바른 생각입니다.
  • hints 2개는 isFactQuestion과 isLeading(9.3)을 모두 통과해야 합니다.
  • leakWords는 그 문제의 문장과 hints에 나오지 않아야 합니다.
  • 맞는 문장 3개는 그 문제의 모든 교과서 본문에 있는 사실이어야 합니다.
  • 맞는 문장이 같은 차시 다른 오개념의 바른 생각을 말하면 안 됩니다. 그러면 다른 문제의 답을 미리 보여 주게 됩니다.
  • "이때", "이 사업"처럼 숨은 문장을 가리키는 말을 쓰지 않습니다. 문장끼리 시간 순서도 맞춥니다.

7.3 만드는 공정 (차시 단위, 하위 에이전트 활용)

  1. 원문 뽑기
    • tools/extract_lessons.py가 PDF의 인쇄 쪽 범위(4장 표)로 차시 글을 뽑아 work/3/chunjae/3-4.txt로 저장합니다.
      • 쪽 번호는 장 아래쪽 두 줄에서 2~3자리 숫자로 찾습니다. "1919년"을 191쪽으로 읽지 않게 숫자 경계를 확인합니다.
      • 한글이 30자 미만이거나 깨진 글자가 10%를 넘는 장은 PNG로도 저장해 눈으로 읽게 합니다.

  2. 초안
    • 초안 에이전트가 원문을 읽고 개념·오개념·같은 뜻 말·오답 탐정 문제를 씁니다.
    • 근거(쪽·문장)는 스크래치 메모로 남깁니다.
  3. 검증
    • 새 맥락의 검증 에이전트(초안을 쓰지 않은 에이전트)가 항목마다 원문과 대조해 직접 고치고 reviewed: true로 바꿉니다.
    • 검증 지시에 꼭 넣을 것은 아래와 같습니다. 초안 에이전트가 흔히 하는 실수들입니다.
      • 내용·차시·쪽이 원문과 맞는가
      • 퀴즈 꼴 질문("어떤 모임일까요?")이 없는가
      • 정답을 품은 질문이 없는가
      • 그 시대에 맞는 말인가(예: 1920년대 이후에는 헌병 경찰이 없음)
      • 원문에 없는 표현("신사를 세워" 등)이 없는가
      • 같은 차시에 함께 나올 다른 문제와 정답이 겹치지 않는가
  4. 겹침 검사
    • tools/check_overlap.js로 같은 범위 문제끼리 "A의 문장에 B의 leakWords가 있는가"를 모두 셉니다.
    • 검증자도 이것은 따로 시키지 않으면 놓칩니다.
  5. 테스트: node --test 전체를 통과시킵니다.
  6. 교사 확인: 교사에게는 JSON이 아니라 review.html(묶음별 표)로 보여 줍니다.

9. AI 호출과 검사

9.1 호출 (llm.js)

연결

  • SDK: https://cdn.jsdelivr.net/npm/@anthropic-ai/sdk@1.13.0/+esm을 동적 import()로 불러옵니다.
  • 클라이언트 옵션: { apiKey, dangerouslyAllowBrowser: true, timeout: 45000, maxRetries: 1 }
  • 키를 숨길 서버가 없으므로, 키는 교사 브라우저에만 둡니다.

요청

  • client.beta.messages.create({ model, max_tokens: 8000, system, messages, output_config: { effort, format: { type: "json_schema", schema } } })
  • 소넷·오퍼스일 때만 betas: ["server-side-fallback-2026-07-01"]을 붙입니다. 하이쿠는 지원하지 않습니다.

모델과 설정

  • 모델: claude-haiku-5-5(기본), claude-sonnet-5-5, claude-opus-5-5
  • 생각하는 정도(effort): low(기본) · medium · high. 설정 화면에는 "낮음(빠름) · 보통 · 높음"으로 보입니다.
  • localStorage 키: sok.apiKey, sok.model, sok.effort
  • 하이쿠를 기본으로 하는 까닭: 소넷의 약 1/20 비용이고, 하이쿠가 흔히 어기는 꼴(길이 넘김, 퀴즈 꼴)은 검사가 잡아 줍니다.

인터페이스

  • llm.call({ system, messages, schema }) → 파싱된 JSON 객체를 돌려줍니다.
  • 서버로 옮길 때는 createClaudeLLM만 바꾸면 되게 둡니다.

주의

  • 구조화 출력은 maxLength를 지원하지 않습니다. 길이는 프롬프트와 검사기로만 잡습니다.
  • 응답은 content 가운데 type: "text" 블록 하나이고, 그 글을 JSON.parse 합니다.

첫 단계에서 반드시 확인 (연기 시험)

  • tests/smoke.html을 만듭니다. 키를 넣은 브라우저에서 열면 아래 최소 요청 한 번을 보내고, 받은 JSON을 보여 줍니다.
const { default: Anthropic } = await import("https://cdn.jsdelivr.net/npm/@anthropic-ai/sdk@1.13.0/+esm");
const client = new Anthropic({ apiKey, dangerouslyAllowBrowser: true, timeout: 45000, maxRetries: 1 });
const msg = await client.beta.messages.create({
  model: "claude-haiku-5-5", max_tokens: 8000,
  system: [{ type: "text", text: "질문 하나를 JSON으로 내세요." }],
  messages: [{ role: "user", content: [{ type: "text", text: "6·25 전쟁" }] }],
  output_config: { effort: "low", format: { type: "json_schema", schema: {
    type: "object", properties: { question: { type: "string" } },
    required: ["question"], additionalProperties: false } } },
});
JSON.parse(msg.content.find((b) => b.type === "text").text);  // → { question: "…요?" }
  • 이 요청이 실패하면 오류 메시지로 원인을 가립니다.
    • SDK 불러오기 실패: jsdelivr 주소나 버전 문제
    • 400: 요청 칸 문제
    • 401: 키 문제
  • 원인을 가린 뒤 Claude API 문서에서 지금 쓰는 칸 이름을 확인해 맞춥니다.
  • SDK를 쓸 수 없으면 fetch("https://api.anthropic.com/v1/messages")로 같은 본문을 보냅니다. 헤더는 x-api-key, anthropic-version: 2023-06-01, anthropic-dangerous-direct-browser-access: true, content-type: application/json입니다.
  • createClaudeLLM만 바꾸면 되도록, 나머지 코드는 llm.call()만 씁니다.

9.2 캐시 구조 (비용 1/5 이하로)

  • system: [시스템 프롬프트, "[오늘 차시 교과서 원문]\n…"(cache_control)]. 원문이 없으면 프롬프트만 넣습니다.

9.3 검사기

공통 질문 검사 (guard.js checkQuestion)

  • 비어 있지 않습니다.
  • 40자 이내입니다.
  • ?로 끝나고 "요?"로 끝나는 존댓말입니다.
  • 한 문장입니다(질문 안에 마침표·느낌표 없음).
  • 금지어(틀렸·정답은·오답)가 없습니다.
  • 앞에서 한 질문과 같지 않습니다(띄어쓰기 무시).

고르기 질문 (isChoice)

  • "~까요, ~까요?"처럼 묻는 말 두 개를 막습니다.
  • "~일까, ~일까요?", "~일까요 ~일까요?"도 막습니다.
  • 앞에 붙은 "있잖아요,", "그런데요," 같은 이어 주는 말은 고르기로 보지 않습니다.

사실 묻기(퀴즈) (isFactQuestion)

  • 아래 꼴을 잡습니다. "왜·까닭·이유·누구를 위해서" 부분은 먼저 지우고 봅니다.
    • 언제
    • 누구가/누구를/누구에게/누구였
    • 무엇을/무엇이었/무엇일까
    • 어디에서/어디였
    • 어떤 일을 한/했
    • "어떤 ○○일까요?"(느낌·마음·기분·생각은 통과)
    • "어느 ○○였을까요?", 문장 중간의 "어느 ○○에서"
    • "어디 ○○였을까요?"
    • 어느/어떤 나라
    • 몇 년/명/개/월
    • "이름을 떠올려"
  • 줄임꼴 "누가"도 잡습니다. 다만 "싸움이 나면 누가 다칠까요?"처럼 "~면" 뒤의 결과를 묻는 질문과 "누가 한 일이 이상한지"는 통과합니다.
  • "~다면/~라면/~려면/~었으면" 가정 질문은 통과합니다.

넌지시 알려 주기 (isLeading)

  • "~지 않았을까요?", "~아닐까요?", "~지 않나요?"처럼 맞장구를 기다리는 질문을 막습니다.

모른다는 말만 함 (isDontKnow, 오답 탐정)

  • 답 전체가 "모른다"는 말일 때만 참입니다. 공백·문장부호·ㅠㅋ는 빼고 봅니다.

예문 (guard.test.js의 고정 사례로 그대로 씁니다. 정규식은 이 사례가 모두 맞게 나오도록 짭니다. 사례는 더해도 되고 빼지 않습니다.)

실패 처리 (모든 방법 공통)

  • 검사에 걸리면 까닭을 알려 주고 다시 받습니다. 예: "42자로 40자를 넘음 — 30자 안팎으로 줄일 것". 같은 요청만 다시 보내면 같은 실수를 되풀이합니다.
  • 다시 받을 때는 응답 형식을 그 단계로만 좁힙니다(예: "질문만" 스키마). 까닭만 알려 주면 AI가 다른 단계로 넘어가 버릴 수 있기 때문입니다.
  • 정한 횟수를 넘기면 기본값으로 대신하고 state.fallbacks를 1 올립니다. 이 횟수는 점검 페이지가 셉니다.
  • 어떤 검사에 걸렸는지도 기록합니다. 기록이 없으면 점검 때 원인을 찾을 수 없습니다.

10. 방법 1 — 엘렌코스

흐름

  1. 입력: "오늘 배운 3가지를 말해 볼까요?" + 칸 3개(빈칸이 있으면 알림)
  2. 확인: 항목마다 확인 표시, 대상 1개, 묻는 방식, 첫 질문
  3. 문답: 질문 카드 1장, 진행 점, 답 칸, [바로 정리하기]
  4. 결과
    • 판정 1개, 세 줄 정리
    • (다시 볼 생각이면) "처음 생각 → 고친 생각"
    • (보류·다시 볼 생각이면) 접힌 선생님 도움말
    • 문답 기록, [복사][인쇄][다음 학생]

확인 표시 (checks)

값화면 글뜻
ok✓원문이나 개념과 맞음. 덜 자세해도 맞음
think더 생각해 볼 것학생 문장 안에 오개념의 틀린 주장이 실제로 있음. 같은 사건이나 낱말이 나오는 것만으로는 아님
unsure교과서에서 함께 찾아봐요주제와 관계있지만 원문·개념에서 확인되지 않고, 어긋나지도 않음
outside오늘 주제와 다른 이야기예요장난, 빈말, "모르겠다"
  • 원문을 주면 AI가 깐깐해집니다. 덜 자세한 맞는 말을 think로 보기 쉬우므로, 위처럼 think를 좁힙니다.
  • "반례를 만들 수 있다고 해서 think로 정하지 않는다"를 프롬프트에 넣습니다. 이 문장이 없으면 맞는 말까지 오개념으로 보는 퇴보가 생깁니다.

대상과 묻는 방식 (코드가 짝을 검사)

mode언제최대 질문
counter 반례think 항목이 있을 때. 대상은 think(여럿이면 오늘 차시와 관계있는 것)3
retry 다시 말해 보기think가 없고 outside가 있을 때3
reason 이유 묻기모두 ok나 unsure일 때. 교과서에 까닭이 나오는 항목만2
  • 검사 규칙
    • checks가 3개이고, target은 0~2입니다.
    • counter의 대상은 think입니다.
    • think가 있으면 reason이 될 수 없습니다.
    • retry의 대상은 ok나 unsure가 아닙니다.
  • misconception(오개념 id)은 범위 안의 id일 때만 받아들입니다. 도움말에 씁니다.

반례 질문 만드는 법 (프롬프트에 넣을 규칙)

  • 첫 질문은 학생 말이 맞다면 어떻게 되는지 묻습니다. 또는 상식이나 오늘 배운 것으로 쉽게 답할 수 있는 것을 묻습니다.
    • 예: "다친 사람은 군인뿐이었다" → "전쟁이 난 곳에는 군인만 살고 있었을까요?"
  • 다음 질문은 학생이 인정한 말을 처음 한 말과 나란히 놓아, 둘이 함께 맞을 수 있는지 묻습니다. 결론은 학생이 말하게 합니다.
  • 학생이 까닭을 대면 그 까닭을 시험합니다.
    • 예: "싸운 건 군인이니까요" → "싸우지 않은 사람은 전쟁에서 다치지 않을까요?"
  • "모르겠어요"라고 하면, 그 사실을 몰라도 답할 수 있는 더 쉬운 질문으로 바꿉니다.
  • 학생이 되물으면 판정하지 않고, 답을 알려 주지 않는 질문으로 이어 갑니다.
  • 이유 묻기에서 방향은 맞지만 근거가 빠지면, 그 까닭을 찾게 하는 질문을 한 번 더 합니다.
    • 예: "나라를 구하기 위해서" → "무엇으로부터 나라를 구하려 했을까요?"

판정 (verdict)

값라벨언제
strong튼튼한 생각반례에도 교과서 근거를 대며 지킴. 이유 묻기로 근거 있게 설명함(이때 문구는 "까닭을 스스로 설명했어요")
revisit다시 볼 생각 → "모르는 것을 알게 되었어요"학생이 스스로 허점을 인정하거나 대상 항목을 고쳐 말함. "제 말이 맞는지 모르겠어요"도 포함
hold판정 보류 → "선생님과 더 이야기해 봐요"어느 쪽도 아님. 근거 없이 끝까지 고집함. "몰라요"만 함

세 줄 정리

  • 응답에서 칸 이름 learned, rethought, nextQuestion으로 받고, 앱 안에서 배열로 바꿉니다.
    • 배열로만 받으면 AI가 학생의 3가지를 그대로 옮겨 적기 쉽습니다. 이름 붙은 칸이 각 줄의 할 일을 정해 줍니다.
  • 줄마다 30자 안팎, 40자 이내입니다.
  • 쓰지 않는 말: 금지어, 칸 이름 붙이기("알게 된 것:"), "반례", "학생이" 같은 3인칭
  • learned: 학생이 맞게 말한 것만 씁니다. 보류일 때는 학생이 끝까지 고치지 않은 항목의 바른 내용을 적지 않습니다.
  • rethought
    • revisit: 고친 생각을 사실 문장으로 씁니다. "처음에는·고쳤다" 같은 과정 말은 쓰지 않습니다.
    • hold: 학생이 한 생각을 "~라고 생각했어요"로 씁니다.
    • strong: 학생이 댄 근거를 씁니다.
  • nextQuestion: "요?"로 끝나는 질문 1개입니다.

호출과 실패 처리

호출언제형식검사 실패 시
check3가지 제출checks, target, mode, misconception, question2번 다시 → checks 모두 unsure(확인 표시 숨김), mode reason, target 0, 기본 질문 "왜 그렇게 생각했나요?"
next답(질문이 남았을 때)stage question 또는 verdict질문만 형식으로 2번 다시 → 기본 질문

  • 응답 칸 (output_config.format의 JSON 스키마. 칸마다 description에 뜻과 글자 수를 적습니다)

    칸값뜻
    stagecheck: check / next: question·verdict / verdict: verdict / 다시 받기: question이 응답이 무엇인지
    checksok·think·unsure·outside 3개 (check만)항목마다 확인 표시
    target0·1·2 (check만)물을 항목
    modecounter·reason·retry (check만)묻는 방식
    misconception오개념 id 또는 "none" (check만)대상 항목의 오개념
    question문자열, 40자 이내다음 질문. 판정할 때는 ""
    verdictstrong·revisit·hold, 질문할 때는 none판정
    summary{learned, rethought, nextQuestion}세 줄 정리. 질문할 때는 세 칸 모두 ""
    • 다시 받기 형식은 stage를 question, verdict를 none으로만 열어 둡니다.

  • 끝내는 때

    • 질문 수 상한(3번, 이유 묻기 2번)은 코드가 지킵니다. 상한에 닿으면 코드가 verdict를 부릅니다.
    • 상한 전이라도 학생 답으로 판정이 분명하면, AI는 next에서 stage verdict를 내어 일찍 끝낼 수 있습니다. 일부러 허용한 것입니다.
      • 예: 첫 반례에 바로 "아, 군인만이 아니었네요"라고 고쳐 말한 학생에게 같은 질문을 더 하지 않으려는 것입니다.
    • 학생이 되물었을 때는 판정하지 않도록 프롬프트가 막습니다.

  • 기본 세 줄: "오늘 배운 것을 세 가지로 말해 보았어요" / "선생님과 함께 다시 생각해 볼 거예요" / "다음 시간에 오늘 생각을 다시 확인해 볼까요?"

  • check 기본값의 확인 표시를 think로 두지 않습니다.

    • 그러면 AI가 실패했을 뿐인데 학생 화면의 세 항목 모두에 "더 생각해 볼 것"이 떠서 원칙(3장)에 어긋납니다.

  • reason 대상(교과서에 까닭이 나오는 항목)이 하나도 없을 때

    • AI가 target 0에 "왜 그렇게 생각했나요?"처럼 학생 생각을 묻는 질문을 냅니다.
    • 학생이 답하면 판정합니다.

11. 방법 2 — 모르는 친구

흐름

  1. 입력: "친구에게 오늘 배운 것을 설명해 볼까요?" 한 칸
    • 예시 글: "예) 오늘은 ~을 배웠어요. ~해서 ~가 되었어요."
  2. 문답
    • 학생 설명이 작게 보입니다.
    • 친구의 질문이 최대 3개 이어지고, 질문 위에 친구의 짧은 반응이 붙습니다.
  3. 결과
    • 질문마다 표시, 친구의 한마디, 다음 시간 확인할 것
    • 선생님 도움말("살펴볼 질문"), 기록, [복사][인쇄][다음 학생]

질문 종류 (코드가 차례를 정하고, 응답 형식의 kind enum을 그 목록으로 좁힘)

차례고를 수 있는 종류
1번meaning 뜻·까닭, more 더 말해, retry 다시 말해
2번mixup 잘못 알아듣기(쓸 오개념이 없으면 meaning)
3번meaning 또는 mixup
  • mixup: 친구가 학생 설명을 오개념의 틀린 생각 쪽으로 받아들여, 그 생각을 믿는 말투로 되묻습니다.
    • 예: "많은 사람이 다쳤어요" → "그럼 싸운 군인들만 다친 거예요?"
    • 학생이 말한 화제와 이어지는 오개념만 씁니다(안 됨: 쌀 이야기를 안 한 학생에게 쌀 오개념).
    • 범위 안의 id여야 하고, 이미 쓴 오개념은 다시 쓰지 않습니다.
  • 퀴즈를 내지 않습니다. 학생이 이미 쓴 낱말의 뜻이나 까닭을 묻는 것은 괜찮습니다.

표시 (앞 질문의 종류와 짝)

앞 질문표시
mixupcorrected 친구를 바로잡았어요(바른 생각이나 까닭을 말함) / together 함께 더 알아봐요
그 밖explained 잘 설명했어요 / together
  • "아니에요"만 하고 까닭이 없거나, 맞장구·"몰라요"·되물음이면 together입니다.
  • 표시 색: 초록(잘 설명), 청록(바로잡음), 호박색(함께 더)

반응·끝맺음 규칙과 검사

  • 반응
    • 20자 이내, 물음표 없이 씁니다. 비워도 됩니다.
    • 칭찬·맞장구를 쓰지 않습니다. 학생이 틀렸을 때도 "맞아요"가 나오기 때문입니다.
      • 막는 꼴: 맞아·맞네·맞죠·맞습니다·맞군요·맞구나, 잘했, 정답, 훌륭
      • "총에 맞아서", "비를 맞아도"처럼 뒤에 서·도·야가 붙은 "맞아"는 통과합니다.
    • 존댓말로 씁니다. 반응을 쉼표·마침표·느낌표로 나눈 마디마다 끝을 봅니다.
      • 막는 끝: ~구나·~네·~어·~다·~지·~래 등
      • 통과: 한 글자 감탄사, 우와·아하·이야, "~니다"
    • 장난에는 맞장구치지 않고 "음, 나는 잘 모르겠어요."처럼 담담하게 받습니다.
  • 끝맺음
    • thanks: 40자 이내입니다. 학생이 맞게 설명한 것만 넣고, 3인칭을 쓰지 않습니다.
    • nextQuestion: 질문 검사를 통과해야 하고, 고르기 꼴이 아니어야 합니다.
  • 기본값
    • 기본 질문: 뜻 "조금 더 자세히 알려 줄래요?", 더 "그래서 어떻게 되었는지 더 알려 줄래요?", 다시 "오늘 배운 것 하나만 알려 줄래요?"
      • 이미 한 질문은 다시 쓰지 않습니다.
      • "몰라요"나 6자 이하 설명이면 "오늘 배운 것 하나만"부터 씁니다.
    • 기본 끝맺음: "설명해 줘서 고마워요!" / "오늘 배운 것을 다음 시간에 다시 말해 볼까요?"
  • 표시는 따로 지킵니다. 질문이나 반응만 검사에 걸렸고 표시가 맞았으면 그 표시를 씁니다.
    • 맞게 답한 학생이 반응 한 줄 때문에 "함께 더 알아봐요"로 바뀌면 안 됩니다.

호출 구조 (정한 것)

  • 학생 답 1번에 호출 1번입니다.

    • 한 응답에 앞 답의 표시 + 반응 + 다음 질문을 함께 받습니다(stage "ask").
    • 마지막 답 뒤에는 표시 + 한마디 + 다음 시간 질문을 받습니다(stage "finish").

  • 첫 호출은 학생 설명만 보고 첫 질문을 냅니다(mark "none").

  • 이 구조에서는 "맞장구친 뒤 바른 생각이 새는 문제"가 생깁니다. 그래서 아래처럼 그 경우에만 다시 받습니다.

  • 응답 칸 (코드가 호출마다 kind와 mark의 enum을 좁혀 스키마를 만듭니다)

    칸값뜻
    stageask 또는 finish다음 질문인지 끝맺음인지
    mark앞 질문 없음: none / 앞이 mixup: corrected·together / 그 밖: explained·together앞 답의 표시
    kind이번 차례에 고를 수 있는 종류만 (ask만)질문 종류
    misconceptionmixup일 때만 오개념 id, 아니면 "none" (ask만)잘못 알아듣기에 쓴 오개념
    reaction20자 이내 (ask만)친구의 짧은 반응
    question40자 이내 (ask만)친구의 질문
    thanks40자 이내 (finish만)친구의 한마디
    nextQuestion질문 1개 (finish만)다음 시간 확인할 것

맞장구친 오개념 (정답 새기 막기)

  • 학생이 친구의 틀린 생각에 맞장구치면(mixup 뒤 together), 같은 응답에 온 다음 질문에 바른 생각이 섞이기 쉽습니다.
    • 그 응답의 질문(또는 끝맺음)은 버리고, 표시는 둔 채 다시 받습니다.
  • 그 뒤 모든 호출에 "[주의] 오개념 X의 바른 생각은 질문·반응·한마디·다음 시간 확인할 것 어디에도 넣지 마세요"를 붙입니다.
    • 바로 다음 호출만 막으면 마지막 한마디에서 샙니다.
  • 바로잡아 주는 것은 교사의 몫입니다.

12. 방법 3 — 오답 탐정

흐름

  1. 안내: "친구의 정리에서 이상한 곳을 찾아볼까요?" + [시작]
  2. 문제
    • "친구가 배운 것을 이렇게 정리했어요. 한 곳이 이상해요." + 문장 카드 ①~④ + 진행 점
    • 앞 차시 문제면 "앞에서 배운 내용 복습" 표시를 붙입니다.
  3. 아무 카드를 눌러도 똑같이 "이 문장이 왜 이상한가요?"와 까닭 칸이 나옵니다.
    • 보내기 전에는 맞는 문장인지 알려 주지 않습니다.
    • 쓰던 글은 다른 카드를 눌러도 남깁니다.
  4. 보낸 뒤
    • 맞는 문장을 고른 경우: AI 없이 고정 문구로 답합니다.
      • "생각을 말해 줘서 고마워요. 다른 문장도 다시 읽어 볼까요?" 그 카드는 흐리게 합니다.
      • 두 번째면 "이 문제는 선생님과 함께 알아봐요." → 함께 더 알아봐요(호박색)
    • 숨은 문장을 고른 경우: AI가 판단합니다.
      • 핵심에 닿으면 까닭까지 밝혔어요(초록)
      • 아니면 이어 묻는 질문(최대 2번) 뒤 마지막 판단 → 밝혔어요 또는 이상한 곳을 찾았어요(청록)
    • 이어 묻는 질문에 모른다는 말만 하면(몰라요·모르겠어요·글쎄요·기억이 안 나요 등) AI를 부르지 않습니다.
      • "이상한 곳을 찾았어요. 까닭은 선생님과 함께 더 알아봐요."로 마무리합니다.
      • 내용이 섞인 답("잘 모르겠지만 군인이요")은 AI가 판단합니다.
      • 처음 까닭 칸에 쓴 "몰라요"는 여기에 들지 않습니다. 이때는 AI가 쉬운 질문을 한 번 냅니다.
  5. [다음 문제] → 2문제 뒤 결과
    • 마지막 문제의 문구: "까닭까지 찾아냈어요! 결과를 볼까요?" / "이 문제는 선생님과 함께 알아봐요. 결과를 볼까요?"
    • 결과 화면
      • 문제마다 표시와 4문장(찾은 문제만 숨은 문장 표시), 나의 까닭
      • 접힌 도움말: 오개념·차시·쪽, 학생이 이상하다고 본 맞는 문장과 그 까닭
      • 기록, [복사][인쇄][다음 학생]
  6. [바로 정리하기]는 문답 중, "다음 문제" 화면, 오류 화면에 있습니다.
    • 이어 묻는 중이면 AI가 마지막 판단을 한 뒤 결과로 갑니다.
    • 오류 화면에서 누르면 그때까지의 기록으로 끝냅니다.

응답 형식과 검사

  • 응답 칸

    형식칸값뜻
    judgeresultsolved·ask숨은 문장에 대한 까닭이 핵심에 닿았는지
    question40자 이내, solved면 ""이어 묻는 질문
    finalresultsolved·found이어 묻기가 끝났을 때 마지막 판단
    questionresult, questionask만질문이 검사에 걸렸을 때 다시 받는 좁은 형식
    가정 검사premise, side문자열, friend·truth·other아래 "가정 검사"

  • 판단 근거: 문제의 key·바른 생각, 전체 개념, 원문뿐입니다. 덜 자세하거나 낱말이 달라도 뜻이 맞으면 solved입니다.

  • 질문 검사 순서

    1. checkQuestion
    2. isChoice
    3. 되풀이
    4. isFactQuestion
    5. isLeading
    6. 정답 낱말(leakIn): 그 문제의 leakWords(+같은 뜻 말 무리) 가운데 학생이 아직 말하지 않은 낱말이 질문에 있으면 걸립니다.
      • 같은 뜻 말 무리: 정답 낱말과 같거나 그 낱말로 시작하는 synonyms 무리를 더합니다(정전 → 정전 협정·휴전 협정).
      • 카드에 이미 보이는 낱말은 뺍니다.
      • 학생이 무리 중 하나라도 말하면 무리 전체를 되받아도 됩니다.
      • "중국군"이 "국군"을 끌어오지 않게 합니다.

  • 가정 검사

    • 위를 모두 통과한 질문에 "~다면/~라면/~려면" 가정이 있으면, 검사 AI를 한 번 더 부릅니다.
    • 검사 AI의 응답: { premise: 가정이 그리는 상황, side: "friend" | "truth" | "other" }
    • truth(학생이 아직 말하지 않은 바른 생각을 담음)면 다시 받습니다.
    • 응답이 이상하거나 검사 호출이 실패해도 그 질문은 쓰지 않습니다.
    • 친구 생각을 따라간 가정("늘린 쌀이 그대로 우리 밥상에 남았다면…")은 friend라 통과합니다.

  • 다시 받는 횟수: judge 2번, final 3번

  • 기본 질문 예: "그 부분이 실제로는 어땠는지 말해 줄래요?"

  • 맞는 문장을 누른 기록은 AI에 보내지 않습니다. 도움말로 교사에게만 보입니다.

프롬프트에 넣을 질문 규칙

  • 아니라고만 했으면 "실제로는 어땠을까요?" 쪽으로, 까닭이 빠졌으면 "왜 그렇게 되었을까요?" 쪽으로 묻습니다.
  • 모범 예: "그 문장의 어느 부분이 실제와 다를까요?"
    • 예시를 "○○은 어떤 일을 했을까요?"처럼 쓰면 AI가 그 퀴즈 꼴을 그대로 따라 합니다. 프롬프트의 예시는 모두 허용되는 꼴로만 씁니다.
  • "몰라요"에는 이 문제의 hints와 숨은 문장의 낱말로 더 쉬운 질문을 만듭니다. 예시를 그대로 쓰지 않습니다.
  • 질문을 "그럼"으로 시작하지 않습니다.
  • 가정은 친구의 숨은 문장이 맞다고 쳐 볼 때만 씁니다.

문제 고르기 (pickProblems)

  • 후보: 그 교과서가 든 문제 중 오늘까지 배운 범위에 있는 것
  • 고르는 무리 차례
    1. 오늘 차시의 아직 안 나온 오개념
    2. 앞 차시의 아직 안 나온 오개념(복습 표시)
    3. 오늘 차시
    4. 앞 차시
  • 단원 마무리는 범위 전체에서 고릅니다.
  • 두 문제는 서로 다른 오개념이고, 같은 무리 안에서는 안 낸 문제를 먼저 냅니다. 모두 냈으면 그 무리 기억을 비우고 다시 돕니다.
  • 겹침 정도
    • 2: 첫 문제 카드에 둘째 문제의 정답 낱말이 있음. 풀기 전에 답이 보입니다.
    • 1: 둘째 카드에 첫 문제의 정답 낱말이 있음. 결과 화면에서만 보입니다.
    • 첫 문제는 겹침 2가 아닌 짝이 있는 문제로 고릅니다.
    • 둘째는 위 차례대로 겹침 2가 아닌 문제를 찾고, 어디에도 없을 때만 겹침 2를 냅니다.
  • 낸 문제 기억(SERVED)은 "교과서+차시"마다 브라우저 탭 메모리에만 둡니다. 새로 고치면 처음부터입니다.
  • 확인: 모의 스크립트로 학생 3명씩 여러 번 돌려 아래를 확인합니다.
    • 겹침 2가 0번
    • 모든 문제가 한 번 이상 나옴
    • 오개념이 3개 이상인 차시는 학생 2명까지 오늘 차시 문제만 받음

13. 화면 디자인 — "차분한 튜터"

색과 글꼴

  • 옅은 회색 바탕, 흰 카드, 파란 강조(#1865F2 계열)
  • 글꼴은 Noto Sans KR 하나이고, 질문만 굵게 씁니다.
  • 교실 TV에서 함께 보므로 큰 글씨(기본 32px)와 높은 대비를 씁니다.

문답

  • 말풍선 대화: AI는 왼쪽(동그라미 그림 + 흰 말풍선), 학생 답은 오른쪽(파란 말풍선)
  • 생각 중에는 AI 말풍선 안에 점 세 개를 보여 줍니다.
  • 답 칸은 둥근 입력 칸 + [보내기]이고, [바로 정리하기]는 작은 글자 버튼입니다.
  • 방법별 그림(SVG): 엘렌코스는 물음표, 모르는 친구는 웃는 얼굴, 오답 탐정은 돋보기

오답 탐정 카드와 결과

  • 오답 탐정 카드는 흰 카드이고, 고르면 파란 테두리를 둘러 줍니다.
  • 결과 카드에는 왼쪽 색 띠를 둡니다(초록·파랑·주황).
  • 버튼은 평평하고 둥글게 만듭니다.

지킬 것

  • 빨간색·X·점수는 쓰지 않습니다.
  • 인쇄는 A4 한 장이고, 기록 상자는 펼쳐서 인쇄합니다.
  • 375px 휴대폰 폭에서도 깨지지 않게 합니다. 위 막대는 한 줄로 접어 화면을 덮지 않게 합니다.

18. 설계 원칙 (모든 방법에 적용)

  1. 흐름은 코드가 정합니다. 판정 시점, 질문 수, 실패 처리를 AI에게 맡기지 않습니다.
  2. 까닭을 알려 주고, 형식을 좁혀 다시 받습니다.
  3. 목록보다 이름 붙은 칸으로 받습니다. 칸마다 설명과 글자 수를 붙입니다.
  4. "안 됨" 예를 프롬프트에 그대로 넣습니다. 모범 예시는 허용되는 꼴로만 씁니다. 예시가 금지 꼴이면 AI가 그대로 따라 합니다.
  5. 잡을 수 있는 꼴은 코드 검사로 막습니다. 사실 묻기·고르기·넌지시 알려 주기는 프롬프트만으로는 막히지 않으므로, 처음부터 검사 코드를 넣습니다.
  6. 앞 결과에 따라 다음 출력이 달라져야 하는 곳을 설계 때 정합니다. 표시와 다음 질문을 한 번에 받으면 코드가 끼어들 틈이 없습니다.
    • 모르는 친구는 호출 수를 줄이려고 한 번에 받는 구조를 쓰고, 맞장구일 때만 다시 받습니다(11장).
  7. 글의 차례가 판단을 바꿉니다. 캐시를 위해 글을 옮길 때도 차례는 그대로 둡니다.
  8. 교과서 원문을 줄 때는 오개념 판정 기준을 좁힙니다. 원문을 받은 AI는 깐깐해지므로 "학생 문장 안에 틀린 주장이 실제로 있을 때"만 오개념으로 봅니다.
  9. 데이터는 미리 만들고, 초안과 검증을 다른 맥락으로 나눕니다. AI가 그때그때 틀린 설명을 지어내게 하지 않습니다.
  10. 문제끼리의 정답 겹침은 스크립트로 봅니다.
  11. 점수로는 정답 새기를 못 잡습니다. 결과를 줄마다 읽습니다.
  12. 브라우저 캐시: 파일을 고치면 ?v=를 올리고, 바뀐 코드가 올라왔는지 확인한 뒤 점검합니다.
  13. 브라우저 점검 스크립트는 한 번에 45초 안에 끝나게 나누어 기다립니다.
  14. 브라우저마다 키 저장소가 따로입니다. 점검하는 창의 [설정]에도 키를 넣어야 합니다.
